# 优化8执行设计说明

## 1. `native_log_pipeline` 实施计划

### 1.1 现状与瓶颈

- `LogRecordHandler.emit()` 在 Python 层串行完成异常格式化、去重统计与日志结构化，随后写入批量缓冲并触发事件引擎 [[LogRecordHandler, 356-473:backend/services/system_manager_service.py]]。
- 批量落盘依赖 `_flush_batch_buffer()` 逐条调用 `LogDatabase.add_log_record()`，同样运行在 Python 层并使用 `json.dumps` 序列化扩展字段 [[LogManager.add_log_record, 609-670:backend/services/system_manager_service.py]][[LogDatabase.add_log_record, 111-141:backend/services/system_manager_service.py]]。
- 高频阶段（启动、批量下载）内多次字符串处理与 GIL 锁争用导致主线程延迟增大，事件推送 `Event(EVENT_LOG_RECORD, log_data)` 亦需复制 Python 字典。

### 1.2 扩展设计

| 组件 | 目标 | 说明 |
| --- | --- | --- |
| `LogPipelineHandler` (C++) | 替换 Python Handler | 直接访问 `PyLogRecord` 并在 C 层完成字段提取、异常序列化与去重计数；提供批量缓冲队列和参考计数防止递归。 |
| SQLite 批量写入 | 减少 Python 上下文切换 | 使用 `sqlite3` C API 一次性提交批次；在扩展内部维护锁和定时刷新，避免 Python `threading.Timer`。 |
| 共享内存事件帧 | 降低事件广播开销 | 借助 `native_ipc` 管理共享内存环形缓冲，将结构化日志块直接投递给主进程 `EventEngine` 读取；失败时回退到原有 `Event()` 推送。 |

**接口建议**

```python
import native_log_pipeline

handler = native_log_pipeline.install(
    batch_size=128,
    flush_interval_ms=500,
    sqlite_path="data/terminal.db",
    enable_event_bridge=True,
)

native_log_pipeline.set_fallback(lambda record: python_handler.emit(record))
```

- 环境变量 `NATIVE_LOG_PIPELINE=0` 可跳过扩展，以兼容缺省安装或调试场景。
- 如果安装失败（例如扩展未编译），`install()` 应抛出可捕获的 `RuntimeError`，由 `logging_init` 阶段回退到现有 Python Handler。

### 1.3 集成步骤

1. 在 `LoggingInitStage` 中检测扩展可用性：
   - 若启用，移除 Python 版 `LogRecordHandler`，注入 `LogPipelineHandler`。
   - 将事件桥接回调绑定到现有 `LogManager.publish_log_record()`，保证 UI/事件总线逻辑不变。
2. 为批量数据定义结构化格式（固定头 + JSON/MessagePack 正文），记录版本号，便于兼容旧日志文件。
3. 更新 `LogManager.shutdown()`，在扩展启用时调用 `native_log_pipeline.flush_and_close()` 释放句柄。
4. 暴露配置：`NATIVE_LOG_PIPELINE`（开关，默认开启）、`NATIVE_LOG_PIPELINE_BATCH`（批量大小）、`NATIVE_LOG_PIPELINE_FLUSH_MS`（刷新间隔）。

### 1.4 原型与测试计划

| 阶段 | 内容 | 输出 |
| --- | --- | --- |
| Prototype | C 扩展最小实现，使用 1 万条/秒日志压测，记录 CPU/延迟对比 | 指标报告（CPU、吞吐、平均写入延迟） |
| Integration | 在三进程启动流程中启用扩展，观察 `application_startup.log` 时间戳与事件延迟 | 启动日志样本、性能图表 |
| Regression | 回退模式、自带 Handler 并行测试，确保无死锁/递归 | 自动化脚本 + CI 报告 |


## 2. `native_qhighlighter` 实施计划

### 2.1 现状与瓶颈

- `PythonHighlighter.highlightBlock()` 使用多轮 `re.finditer` 在 Python 层匹配关键字、字符串与注释，滚动大文件时造成 UI 主线程阻塞 [[PythonHighlighter, 880-999:ui/components/widgets.py]]。
- `MonacoEditorWidget` 在初始化时立即创建 `PythonHighlighter`，未提供替换钩子，无法充分利用 Qt C++ 侧的 `QSyntaxHighlighter` 优化 [[MonacoEditorWidget, 1003-1051:ui/components/widgets.py]]。

### 2.2 扩展设计

| 组件 | 目标 | 说明 |
| --- | --- | --- |
| `NativePythonHighlighter` (C++) | 高效 token 化 | 预编译 `QRegularExpression` 集合并在 `highlightBlock` 中一次性扫描，使用 token 表驱动格式化。 |
| Python 绑定 | 无缝接入现有 UI | 通过 shiboken/sip 暴露类并在 `MonacoEditorWidget` 初始化时优先实例化原生版本；若不可用则退回 Python 版本。 |
| 多语言支持 | 可扩展 | 允许通过 JSON/INI 提供关键字与配色，便于未来扩展到脚本/JSON 等语法。 |

**接口建议**

```python
try:
    from native_qhighlighter import NativePythonHighlighter
    self.highlighter = NativePythonHighlighter(self.document(), theme="monaco-dark")
except ImportError:
    self.highlighter = PythonHighlighter(self.document())
```

### 2.3 集成步骤

1. 在 `MonacoEditorWidget` 的 `_setup_editor_style()` 或构造函数中添加原生高亮器探测逻辑。
2. 为 `NativePythonHighlighter` 提供主题配置（颜色、字体权重）映射到 `QTextCharFormat`，保证 UI 视觉一致。
3. 新增 UI 基准测试：加载 10 万行 Python 文件、执行批量替换、滚动等操作并测量帧率。
4. 暴露配置：`NATIVE_QHIGHLIGHTER` 环境变量（默认开启），便于灰度或问题定位。

### 2.4 验证计划

- **性能**：对比原生与 Python 方案的平均帧时间、CPU 利用率；目标 >= 40% 帧时间下降。
- **功能**：编写自动化脚本验证关键 token（关键字、字符串、注释、装饰器）着色一致。
- **兼容**：在快速切换主题/关闭编辑器时确保不崩溃；启用/禁用扩展时 UI 行为一致。


## 3. `native_vnpy_conversion` 实施计划

### 3.1 现状与瓶颈

- `DataConverter` 逐字段访问 VnPy 对象并构造 dataclass，批量转换路径 `batch_convert_vnpy_data()` 仍在循环内调用单条转换，频繁触发属性访问与对象分配 [[DataConverter, 421-620:backend/core/service_base.py]]。
- 在 Tick/Bar 高频场景下，Python 层开销加重 GIL 竞争，并产生大量临时字典/对象。

### 3.2 扩展设计

| 组件 | 目标 | 说明 |
| --- | --- | --- |
| `convert_ticks`, `convert_bars` | 批量零拷贝 | 接受 `Sequence[TickData]`，在 C 层遍历并填充结构化缓冲，返回 `memoryview` 或 Arrow `RecordBatch`。 |
| 元数据封装 | 减少 Python 分配 | 通过预定义结构体（如 `struct UnifiedTick { ... }`）统一字段顺序，便于与 `native_serialization`/`native_memory` 协同。 |
| 回退机制 | 兼容旧路径 | 扩展不可用时回退到原 Python 实现；提供 `use_native=False` 参数强制关闭。 |

**接口建议**

```python
try:
    import native_vnpy_conversion as nvc
    converted = nvc.convert_ticks(tick_list, output="arrow")
except ImportError:
    converted = DataConverter.batch_convert_vnpy_data(tick_list, "tick")
```

- 支持输出模式：`"dict"`（回写 Python dict 列表）、`"arrow"`（Arrow Table）、`"shared"`（共享内存句柄）。
- 暴露 `register_symbol_metadata()` 等辅助接口，为缺省字段（行情频率、数据源）提供默认值，减少 Python 参与度。

### 3.3 集成步骤

1. 在 `DataConverter` 内添加条件分支，优先调用原生实现，保持现有 API 不变。
2. 在数据进程（如 `data_process_main`）中批量处理 RPC 返回值时，直接使用 Arrow 数据返回，配合 `native_log_pipeline` 计划实现端到端零拷贝。
3. 对关键事件（Tick/Bar）增加指标埋点，比较启用/禁用扩展时的平均处理时延。
4. 暴露配置：`NATIVE_VNPY_CONVERSION`（开关，默认开启）、`NATIVE_VNPY_CONVERSION_OUTPUT`（目前仅支持 `dict`）。

### 3.4 验证计划

- **单元测试**：对比原生与 Python 输出的一致性（字段、精度、时间戳）。
- **性能测试**：构造高频 Tick（>100k 条）转化压测，记录 CPU、耗时；目标为处理时间至少下降 40%。
- **稳定性**：在长时间订阅行情的集成测试中运行 >4 小时，确认无内存泄漏或崩溃。


## 4. 风险与验证安排

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| C 扩展编译/部署失败 | 功能回退或启动中断 | 统一使用环境变量/配置开关；在 `LoggingInitStage`、`MonacoEditorWidget`、`DataConverter` 中捕获异常并自动启用 Python 路径。 |
| 跨语言数据格式不兼容 | 数据错误或崩溃 | 为每个扩展定义版本化协议头，新增基线测试验证字段顺序与类型；在 CI 中执行双路径回归。 |
| 共享内存资源泄漏 | 长时运行风险 | 在进程退出钩子中调用扩展 `cleanup()`；编写压力测试确保句柄关闭。 |
| UI 线程安全问题 | 崩溃或卡死 | 在原生高亮器内谨慎处理多线程，遵循 Qt 主线程限制；新增 UI 自动化回归。 |

**CI/验证要求**

- Windows 平台新增 C 扩展编译流水线，生成 `.pyd` 并运行针对性的单元与性能测试。
- 现有 `test_rpc_integration.py`、`test_monitor_integration.py`、`test_batch_performance.py` 增加“扩展开启/关闭”两档运行，确保行为一致。
- 记录性能指标并上传到构建产物，便于对比历史版本。

以上方案对应《优化8》提出的三个新增热点，覆盖接口设计、回退逻辑与验证策略，可按优先级推进实现。
