## 1. 背压控制原理

### 1.1 生产者-消费者模型

星辰金融终端使用多进程+多协程架构进行数据处理:

```
生产者(N个进程 × M个协程)
  ↓
  入队 → [任务队列] → 出队
  ↓                     ↓
result_queue        消费者(主进程)
  (有界队列)          (处理结果)
```

**问题**: 当生产速度 > 消费速度时,队列无限增长导致内存溢出

### 1.2 队列容量管理

**有界队列设计**:
- 最大容量: 10,000项(可配置)
- 填充率监控: 实时计算 `queue.qsize() / max_size`
- 阈值告警:
  - 80% - 高压告警
  - 95% - 严重告警,触发熔断

### 1.3 背压信号传播

```
消费者检测队列积压(填充率>80%)
  ↓
记录WARNING日志
  ↓
(未来)发送背压信号到LoadBalancer
  ↓
LoadBalancer降低批次大小/并发数
  ↓
生产者减速
```

## 2. 队列阻塞/拒绝策略

### 2.1 超时阻塞机制

**核心函数**: [`_safe_put_queue()`](file://c:\Users\USER\Desktop\terminal_v0.50\backend\infrastructure\data_module_vnpy\data_quality.py#L69-L128)

**工作流程**:
1. 尝试入队,阻塞等待最多1秒(可配置)
2. 超时后记录WARNING并跳过任务
3. 统计跳过次数,触发分级告警

**代码示例**:
```python
success = await asyncio.to_thread(
    _safe_put_queue,
    result_queue,
    (symbol, quality_dict),
    timeout=1.0,
    queue_name="result_queue",
    worker_id=worker_id,
)
if success:
    processed += 1
else:
    # 队列满,任务已跳过
    skipped += 1
```

### 2.2 任务跳过逻辑

**统计机制**:
- 按`{queue_name}_{worker_id}`维度统计
- 线程安全(使用threading.Lock)
- 提供查询接口: `_get_queue_skip_stats()`

**告警规则**:
| 跳过次数 | 日志级别 | 触发条件 |
|---------|---------|---------|
| 1-3次 | WARNING | 每次记录 |
| 4-99次 | WARNING | 每10次记录一次 |
| 100次 | ERROR (alert) | 首次达到100次 |
| 500次+ | ERROR (alert) | 每500次记录一次 |

### 2.3 配置参数

**位置**: `config/terminal_config.json` → `backpressure`

```json
{
  "backpressure": {
    "enabled": true,
    "queue_max_size": 10000,
    "queue_put_timeout": 1.0,
    "queue_skip_warning_threshold": 10,
    "consumer_block_timeout": 0.5,
    "queue_pressure_threshold_high": 0.8,
    "queue_pressure_threshold_critical": 0.95
  }
}
```

## 3. 消费者背压反馈

### 3.1 速度监控指标

**监控维度**:
- **队列填充率**: `current_size / max_size`
- **消费速率**: `processed_count / elapsed_time` (items/s)
- **积压时长**: 队列持续满载时间

**实现位置**: 
- `data_quality.py`: 第5018-5038行
- `data_acquisition.py`: (待实施)

### 3.2 阻塞等待改造

**旧实现** (忙等,浪费CPU):
```python
msg = result_queue.get_nowait()  # 非阻塞,队列空时抛异常
```

**新实现** (阻塞等待):
```python
msg = result_queue.get(timeout=0.5)  # 阻塞等待,减少CPU空转
```

### 3.3 背压检测和告警

**检测逻辑**:
```python
queue_size = result_queue.qsize()
if queue_size > 8000:  # 80%填充率
    logger.warning(
        f"⚠️ 队列积压告警: result_queue当前大小={queue_size}, "
        f"消费者可能过慢！"
    )
```

**告警条件**:
| 条件 | 严重级别 | 建议操作 |
|-----|---------|---------|
| 填充率>80% 持续>10秒 | WARNING | 检查消费者性能 |
| 填充率>95% 持续>60秒 | ERROR | 降低并发数 |
| 消费速率<5 items/s 持续>30秒 | WARNING | 优化消费者逻辑 |

## 4. 动态批次调整 (阶段2待实施)

### 4.1 双因素调整模型

**评分公式**:
```
最终批次大小 = 基准批次 × (资源系数 × 0.6 + 队列系数 × 0.4)
```

**因素权重**:
- 资源压力: 60% (CPU/内存/磁盘/网络)
- 队列压力: 40% (填充率)

### 4.2 队列压力评估

**压力映射**:
| 填充率 | 压力等级 | 批次系数 |
|-------|---------|---------|
| 0-50% | 正常 | 1.0x |
| 50-70% | 中等 | 0.8x |
| 70-85% | 高 | 0.5x |
| 85-100% | 严重 | 0.3x |

### 4.3 调整冷却机制

**防振荡设计**:
- 最短调整间隔: 5秒
- 单次调整步长限制: ±20%
- 使用EMA平滑队列压力: `α = 0.3`

## 5. 配置参数说明

### 5.1 队列容量配置

| 参数 | 默认值 | 说明 | 建议范围 |
|-----|-------|------|---------|
| `queue_max_size` | 10000 | 队列最大容量 | 5000-20000 |
| `queue_put_timeout` | 1.0 | 入队超时(秒) | 0.5-3.0 |
| `consumer_block_timeout` | 0.5 | 出队超时(秒) | 0.1-1.0 |

**容量规划建议**:
- **小任务**(如IPO下载): 5000项
- **中等任务**(如数据质量扫描): 10000项
- **大任务**(如历史下载): 20000项

### 5.2 超时和阈值配置

| 参数 | 默认值 | 说明 | 建议范围 |
|-----|-------|------|---------|
| `queue_skip_warning_threshold` | 10 | 连续跳过多少次后告警 | 5-50 |
| `queue_pressure_threshold_high` | 0.8 | 高压阈值(填充率) | 0.7-0.9 |
| `queue_pressure_threshold_critical` | 0.95 | 严重阈值(填充率) | 0.9-0.98 |

### 5.3 调整系数配置

| 参数 | 默认值 | 说明 | 建议范围 |
|-----|-------|------|---------|
| `backpressure_cooldown_seconds` | 5.0 | 调整冷却时间(秒) | 3.0-10.0 |
| `batch_adjustment_max_step` | 0.2 | 批次调整最大步长 | 0.1-0.5 |

## 7. 故障排查指南

### 7.1 常见问题

#### 问题1: 队列持续满载

**症状**:
- 日志中频繁出现"⚠️ 队列满, 跳过任务"
- 任务跳过率>1%
- 队列填充率持续>95%

**诊断步骤**:
1. 检查消费者速度: 是否<10 items/s?
2. 检查系统资源: CPU/内存是否达到瓶颈?
3. 检查数据处理逻辑: 是否有阻塞操作?

**解决方案**:
- **短期**: 降低并发数(减少进程数/协程数)
- **中期**: 优化消费者逻辑,提升处理速度
- **长期**: 增加队列容量或使用分布式队列

#### 问题2: 内存持续增长

**症状**:
- 内存占用持续上升,不回落
- 系统报"MemoryError"
- 进程被OOM Killer杀死

**诊断步骤**:
1. 检查队列大小: `result_queue.qsize()`
2. 检查是否启用背压: `config["backpressure"]["enabled"]`
3. 使用`tracemalloc`分析内存分配

**解决方案**:
- 确认背压控制已启用
- 减小`queue_max_size`
- 检查是否有内存泄漏(未释放的DataFrame)

#### 问题3: 任务大量跳过

**症状**:
- 日志显示累计跳过>100次
- 最终结果缺少大量品种
- 用户反馈数据不完整

**诊断步骤**:
1. 查看跳过统计: `_get_queue_skip_stats()`
2. 检查消费者是否异常退出
3. 检查是否触发熔断(队列填充率>95%)

**解决方案**:
- **临时**: 手动重试跳过的品种
- **调整**: 增加`queue_put_timeout`(如改为2秒)
- **根治**: 优化消费者,提升处理速度

### 7.3 优化建议

**生产者优化**:
- 减少进程数: 从32降到16
- 减少协程数: 从80降到40
- 启用两段式下载: 优先使用最快的30个服务器

**消费者优化**:
- 使用批量处理: 一次处理10个结果而非逐个处理
- 异步I/O: 数据库写入使用异步模式
- 减少日志: 调整日志级别,减少DEBUG输出

**队列优化**:
- 增加容量: 从10000改为20000(需要足够内存)
- 启用优先级: 重要品种优先处理
- 分离队列: 成功/失败使用不同队列
