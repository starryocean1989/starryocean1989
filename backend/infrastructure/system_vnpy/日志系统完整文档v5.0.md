## 二、问题分析

### 2.1 核心问题

1. **日志粒度不足**: 未按场景/模块精细化控制，控制台噪音大
2. **缺少场景感知**: 启动/下载/交易阶段日志策略一致，调试困难
3. **模块未隔离**: 高频下载日志淹没策略执行日志
4. **用户角色未区分**: 开发/生产/运维模式日志需求不同

### 2.2 具体表现

- **启动阶段**: 需要详细日志排查问题，但与运行时混在一起
- **下载阶段**: 15000个任务产生300条/秒进度日志，淹没控制台
- **交易阶段**: 订单日志需要全量入库审计，但当前INFO不入库
- **调试场景**: 开发时需要DEBUG全量，生产时不需要

## 三、设计原则

### 3.1 核心原则

1. **分层路由**: 全局规则 → 阶段规则 → 模块规则 → 场景规则（优先级递增）
2. **用户角色感知**: 开发模式(DEBUG全量) vs 生产模式(INFO+节流) vs 运维模式(告警强化)
3. **动态策略切换**: 按生命周期阶段自动切换日志策略
4. **性能优先**: 节流+批量写入+异步分发+规则缓存
5. **可观测性**: 统计信息+日志追踪+告警联动

### 3.2 设计目标

- **减少噪音**: 控制台输出减少60%（过滤DEBUG和PROGRESS）
- **精准路由**: 不同阶段使用不同策略（启动详细、下载静默、交易全记录）
- **性能优化**: 路由耗时<0.1ms（缓存后<0.01ms），缓存命中率>95%
- **易维护**: YAML外部配置，支持热更新，无需重启

## 四、四层路由架构（v5.0版）

### 4.1 架构图

```
应用层（任何模块）
    ↓ logging.getLogger().xxx()
LoggingHub（托管模式，唯一入口）
    ↓
RoutingRuleEngine（四层决策+缓存优化）
    ├─ Layer 4: 场景规则 (scenario_bulk_download)  ← 最高优先级
    ├─ Layer 3: 模块规则 (module_data_center)
    ├─ Layer 2: 阶段规则 (stage_downloading)
    └─ Layer 1: 全局规则 (global_defaults)         ← 最低优先级（兜底）
    ↓
RuleCache（5秒TTL缓存）
    ↓
多渠道分发
    ├─ Console (StreamHandler托管)
    ├─ File (FileHandler托管)
    ├─ AI File (AILogFileHandler) ← v5.0整合
    ├─ Database (SQLite批量写入)
    ├─ EventEngine (VNPY事件，节流)
    ├─ UI (StatusBar/Dialog)
    └─ ZMQ (监控进程回传)

所有组件整合在：unified_log_system.py（1194行，9个Part）
```

### 4.2 Layer 1: 全局默认规则

**用途**: 兜底规则，未被其他层覆盖时使用

**配置文件**: `config/rules_global.yaml`

**规则示例**:
```yaml
SYSTEM:
  DEBUG: [file]
  INFO: [file, console]
  WARNING: [file, console, database, event]
  ERROR: [file, console, database, event]
  CRITICAL: [file, console, database, event, ui_dialog]

PROGRESS:
  INFO: [file, event_throttled]  # 不输出到控制台
  WARNING: [file, console, event]

ALERT:
  WARNING: [file, console, database, statusbar, event]
  ERROR: [file, console, database, statusbar, ui_dialog, event]
```

**设计原则**:
- 控制台静音: DEBUG和PROGRESS.INFO不输出（减少60%噪音）
- 数据库精简: 仅WARNING+级别（减少95%存储）
- 关键弹窗: 仅ERROR+的ALERT/SYSTEM

### 4.3 Layer 2: 阶段规则

**用途**: 按生命周期阶段切换策略

**配置文件**: `config/rules_stage.yaml`

**8个阶段定义**:

| 阶段 | 代码 | 持续时间 | 策略特点 |
|------|------|---------|---------|
| 启动 | stage_startup | 5-10秒 | DEBUG也输出，便于排查启动问题 |
| 数据感知 | stage_sensing | 10-30秒 | 进度显示在状态栏 |
| 下载 | stage_downloading | 1-3分钟 | 进度静默，完成通知仅状态栏 |
| 质量扫描 | stage_quality_scan | 30-60秒 | 质量告警入库 |
| 交易 | stage_trading | 持续 | INFO也入库，告警发邮件/短信 |
| 回测 | stage_backtest | 1-5分钟 | 回测完成弹窗 |
| 监控 | stage_monitoring | 持续 | 通过ZMQ推送到主进程 |
| 关闭 | stage_shutdown | 3-5秒 | 清理日志 |

**规则示例**:
```yaml
# 启动阶段: 详细输出
stage_startup:
  SYSTEM:
    DEBUG: [file, console]  # 启动阶段DEBUG也输出
    INFO: [file, console]
  PROGRESS:
    INFO: [file, console]   # 启动进度输出到控制台

# 下载阶段: 静默模式
stage_downloading:
  PROGRESS:
    INFO: [file, event_throttled]  # 不输出到控制台
  NOTIFICATION:
    INFO: [file, statusbar, event]  # 完成通知仅状态栏

# 交易阶段: 全量记录
stage_trading:
  SYSTEM:
    INFO: [file, database]  # INFO也入库（订单追踪）
  ALERT:
    ERROR: [file, database, statusbar, ui_dialog, event, email]
    CRITICAL: [file, database, statusbar, ui_dialog, event, email, sms]
```

```yaml
    ERROR: [file, database, statusbar, ui_dialog, event, email]
```

### 4.6 路由决策流程

```python
def route(self, record: UnifiedLogRecord) -> List[str]:
    """四层路由决策"""
    # 构造缓存键
    cache_key = (log_type, level, module, scenario, current_stage)

    # 先查缓存（性能优化）
    cached = self.cache.get(cache_key)
    if cached:
        return cached

    # Layer 4: 场景规则（最高优先级）
    if scenario and scenario in scenario_rules:
        targets = scenario_rules[scenario][log_type][level]
        if targets:
            self.cache.set(cache_key, targets)
            return targets

    # Layer 3: 模块规则
    for module_config in module_rules:
        if module_matches(record.module, module_config):
            targets = module_config[log_type][level]
            if targets:
                self.cache.set(cache_key, targets)
                return targets

    # Layer 2: 阶段规则
    stage_config = stage_rules[current_stage]
    targets = stage_config.get(log_type, {}).get(level)
    if targets:
        self.cache.set(cache_key, targets)
        return targets

    # Layer 1: 全局规则（兜底）
    targets = global_rules[log_type][level]
    self.cache.set(cache_key, targets)
    return targets
```

```python
class RuleCache:
    """规则缓存（LRU+TTL）- v5.0整合版本"""
    def __init__(self, ttl_seconds: int = 5):
        """初始化缓存"""
        self.ttl = ttl_seconds
        self._cache: Dict[Tuple, Any] = {}
        self._lock = Lock()
        self._hits = 0
        self._misses = 0

    def get(self, key: Tuple) -> Optional[List[str]]:
        """获取缓存（检查TTL）"""
        cached = self._cache.get(key)
        if cached and not self._is_expired(cached):
            self._hits += 1
            return cached['targets']
        self._misses += 1
        return None

    def set(self, key: Tuple, targets: List[str]):
        """设置缓存"""
        self._cache[key] = {
            'targets': targets,
            'timestamp': time.time()
        }

    def clear(self):
        """清空缓存（阶段切换时）"""
        self._cache.clear()

    def get_statistics(self) -> Dict:
        """获取统计信息"""
        total = self._hits + self._misses
        hit_rate = (self._hits / total * 100) if total > 0 else 0
        return {
            "size": len(self._cache),
            "hits": self._hits,
            "misses": self._misses,
            "hit_rate": hit_rate
        }
```

## 三、反模式清单

### 3.1 反模式1: 过度日志

**问题**: 记录不必要的详细信息

**错误示例**:
```python
# ❌ 记录每次循环

    logger.debug("循环第 %d 次", i)

# ❌ 记录中间变量

```

**正确示例**:
```python
# ✅ 仅记录关键节点
logger.info("开始处理，共 %d 条数据", total)
# ... 处理逻辑 ...
logger.info("处理完成，耗时 %.2f 秒", elapsed)
```

### 3.2 反模式2: 日志级别误用

**问题**: 使用错误的日志级别

**错误示例**:
```python
# ❌ 正常流程用WARNING
logger.warning("开始下载数据")

# ❌ 异常情况用INFO
logger.info("连接失败，无法下载")

# ❌ 调试信息用ERROR
logger.error("调试信息: a=%d, b=%d", a, b)
```

**正确示例**:
```python
# ✅ 正常流程用INFO
logger.info("开始下载数据")

# ✅ 异常情况用ERROR
logger.error("连接失败，无法下载: %s", error)

# ✅ 调试信息用DEBUG
logger.debug("调试信息: a=%d, b=%d", a, b)
```

**日志级别使用规范**:
- **DEBUG**: 调试信息，生产环境不输出
- **INFO**: 正常流程，关键节点
- **WARNING**: 警告信息，非致命问题
- **ERROR**: 错误信息，影响功能
- **CRITICAL**: 严重错误，系统崩溃

### 3.3 反模式3: 字符串拼接

**问题**: 性能损失 + 安全风险

**错误示例**:
```python
# ❌ 字符串拼接

# ❌ f-string（不支持lazy formatting）

```

**正确示例**:
```python
# ✅ 使用%格式化（lazy formatting）
logger.info("用户: %s，操作: %s", username, action)
```

### 3.4 反模式4: 缺少上下文

**问题**: 信息不足，无法定位问题

**错误示例**:
```python

# ❌ 缺少关键参数
```

**正确示例**:

## 二、YAML配置详解

### 2.1 rules_global.yaml（全局默认规则）

**用途**: 兜底规则，未被其他层覆盖时使用

**配置示例**:
```yaml
SYSTEM:
  DEBUG: [file]
  INFO: [file, console]
  WARNING: [file, console, database, event]
  ERROR: [file, console, database, event]
  CRITICAL: [file, console, database, event, ui_dialog]

PROGRESS:
  INFO: [file, event_throttled]  # 不输出到控制台
  WARNING: [file, console, event]
  ERROR: [file, console, database, event]

NOTIFICATION:
  INFO: [file, console, statusbar, event]
  WARNING: [file, console, database, event]
  ERROR: [file, console, database, event]

ALERT:
  WARNING: [file, console, database, statusbar, event]
  ERROR: [file, console, database, statusbar, ui_dialog, event]
  CRITICAL: [file, console, database, statusbar, ui_dialog, event]

USER_FEEDBACK:
  INFO: [statusbar]
  ERROR: [ui_dialog]

DEBUG:
  DEBUG: [file]
```

**设计原则**:
- 控制台静音: DEBUG和PROGRESS.INFO不输出（减少60%噪音）
- 数据库精简: 仅WARNING+级别（减少95%存储）
- 关键弹窗: 仅ERROR+的ALERT/SYSTEM

### 2.2 rules_stage.yaml（阶段规则）

**8个阶段定义**:

#### 1. 启动阶段 (stage_startup, 5-10秒)

```yaml
stage_startup:
  description: "系统启动和初始化阶段"
  duration: "5-10s"
  SYSTEM:
    DEBUG: [file, console]  # 启动阶段DEBUG也输出
    INFO: [file, console]
  PROGRESS:
    INFO: [file, console]   # 启动进度输出到控制台
```

**特点**: 详细输出，便于排查启动问题

#### 2. 数据感知阶段 (stage_sensing, 10-30秒)

```yaml
stage_sensing:
  description: "数据感知和缓存验证阶段"
  duration: "10-30s"
  PROGRESS:
    INFO: [file, event_throttled, statusbar]  # 进度显示在状态栏
```

**特点**: 进度显示在状态栏，不干扰控制台

#### 3. 下载阶段 (stage_downloading, 1-3分钟)

```yaml
stage_downloading:
  description: "批量数据下载阶段（高频日志）"
  duration: "1-3min"
  PROGRESS:
    INFO: [file, event_throttled]  # 不输出到控制台
  NOTIFICATION:
    INFO: [file, statusbar, event]  # 完成通知仅状态栏
```

**特点**: 静默模式，减少噪音（15000任务产生高频日志）

#### 4. 质量扫描阶段 (stage_quality_scan, 30-60秒)

```yaml
stage_quality_scan:
  description: "数据质量扫描阶段"
  duration: "30-60s"
  ALERT:
    WARNING: [file, database, statusbar]  # 质量问题入库
```

**特点**: 质量告警入库，便于追溯

#### 5. 交易阶段 (stage_trading, 持续运行)

```yaml
stage_trading:
  description: "实盘交易阶段（关键阶段）"
  duration: "持续"
  priority: critical
  SYSTEM:
    INFO: [file, database]  # INFO也入库（订单追踪）
  ALERT:
    ERROR: [file, database, statusbar, ui_dialog, event, email]  # 发邮件
    CRITICAL: [file, database, statusbar, ui_dialog, event, email, sms]  # 发短信
```

**特点**: 全量记录，所有日志入库，告警强化

#### 6. 策略回测阶段 (stage_backtest, 1-5分钟)

```yaml
stage_backtest:
  description: "策略回测阶段"
  duration: "1-5min"
  NOTIFICATION:
    INFO: [file, statusbar, ui_dialog]  # 回测完成弹窗
```

**特点**: 回测完成弹窗提示

#### 7. 监控阶段 (stage_monitoring, 持续运行)

```yaml
stage_monitoring:
  description: "系统监控阶段（独立进程）"
  duration: "持续"
  ALERT:
    WARNING: [file, zmq_push, statusbar]  # 通过ZMQ推送到主进程
```

**特点**: 独立进程，ZMQ回传

#### 8. 关闭阶段 (stage_shutdown, 3-5秒)

```yaml
stage_shutdown:
  description: "系统关闭和清理阶段"
  duration: "3-5s"
  SYSTEM:
    INFO: [file, console]
```

**特点**: 清理日志，确保所有日志写入

## 六、故障排查指南

### 问题1: 配置验证失败

**症状**: 启动时提示"路由规则配置验证失败"

**排查步骤**:
1. 运行`rule_validator.py`查看详细错误
   ```bash
   python backend/infrastructure/system_vnpy/rule_validator.py
   ```
2. 检查YAML语法（缩进、冒号、引号）
3. 检查日志类型/级别/目标是否合法

### 问题2: 路由引擎初始化失败

**症状**: 日志显示"路由引擎初始化失败: xxx"

**排查步骤**:
1. 检查config目录是否存在
2. 检查4个YAML文件是否存在
3. 检查YAML文件是否可读（权限）

### 问题3: 阶段切换不生效

**症状**: 调用set_stage后，日志输出未改变

**排查步骤**:
1. 检查是否正确获取LoggingHub实例
2. 检查stage名称是否正确（与YAML中一致）
3. 检查缓存是否清空（阶段切换会自动清空）

### 问题4: 场景上下文不生效

**症状**: 使用场景上下文后，仍使用全局规则

**排查步骤**:
1. 检查scenario名称是否正确（不带`scenario_`前缀）
2. 检查YAML中是否定义了该场景规则
3. 检查场景规则是否正确配置

### 问题5: 性能不达标

**症状**: 路由耗时>0.1ms或缓存命中率<95%

**排查步骤**:
1. 检查缓存TTL设置（默认5秒）
2. 检查是否频繁切换阶段（会清空缓存）
3. 运行性能测试脚本，查看详细统计

## 八、AI日志系统（v4.1新增）

### 8.1 设计目标

**问题**:
- Terminal输出简洁后，用户发现问题无法获取详细信息
- 日志文件`backend.log`所有流程混在一起，难以定位问题
- 系统崩溃时无法知道断点位置

**解决方案**:
- 为每个关键流程创建独立的AI日志文件
- 实时写入，即使崩溃也能保留断点
- 为AI助手优化的详细格式，便于理解和debug

### 8.2 文件命名规范

**基本格式**:
```
logs/ai/[流程名称]_[时间戳].log
```

**示例**:
```

logs/ai/symbol_refresh_20250128_143125.log      # 品种列表刷新
logs/ai/download_kline_20250128_143225.log      # K线数据下载
logs/ai/quality_scan_20250128_143325.log        # 数据质量扫描
logs/ai/strategy_backtest_20250128_143425.log   # 策略回测
```

### 8.7 使用建议

#### 8.7.1 何时使用AI日志流程

✅ **应该使用**:
- 用户主动触发的操作（手动下载、手动扫描等）
- 长时间运行的任务（批量下载、质量扫描）
- 可能失败的关键流程（策略回测、交易执行）
- 需要详细调试信息的流程

❌ **不应该使用**:
- 简单的查询操作
- 高频调用的函数
- 已经在其他AI日志流程内部的子流程
- 系统内部初始化（除非独立流程）

#### 8.7.2 日志级别选择

- **DEBUG**: 详细的调试信息（步骤、变量值、配置参数）
- **INFO**: 流程关键节点（开始、完成、中间里程碑）
- **WARNING**: 非致命问题（数据缺失、超时重试）
- **ERROR**: 严重错误（失败、异常）

#### 8.7.3 元数据设计

- 包含关键参数（品种数量、时间范围）
- 便于AI理解上下文
- 不要包含敏感信息

#### 8.7.4 异常处理

- 使用`logger.exception()`记录完整堆栈
- 在`end_ai_process()`中标记失败
- 包含失败原因摘要

### 8.10 性能影响

**额外开销**:
- 文件I/O: 实时写入，但buffering=1减少系统调用
- 内存: 忽略不计（只保留当前文件句柄）
- CPU: 日志格式化开销，但与普通文件日志相同

**优化**:
- 无缓冲写入确保崩溃安全
- 每个流程独立文件，避免锁竞争
- 只在有活动流程时才写入

**建议**:
- 不要嵌套使用（避免多层文件）
- 高频操作不要使用AI日志流程
