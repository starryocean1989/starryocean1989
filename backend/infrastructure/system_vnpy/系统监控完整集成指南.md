| --- | --- | --- | --- | --- |

### 新架构文件结构（v1.0重构版）

```
system_vnpy/

├── monitor_toolkit.py        (~2500行 - 监控工具集)
│   ├── Part 1: 管理员权限工具

│   └── Part 6: 网络工具（NetworkTester、PortScanner）
│
└── config/
    ├── system_config.yaml         # 系统监控配置（新增）
    ├── threshold_config.yaml      # 阈值配置（新增）
    ├── speedtest_servers.yaml     # 带宽测试配置
    ├── ping_servers.yaml          # 延迟测试配置（新增）
```

**文件统计**:
- `core_engine.py`: 核心引擎 + 配置管理 + 缓存管理 + 事件系统
- `monitor_system.py`: 23类 + 5函数 + 24异步方法（监控核心）
- `monitor_toolkit.py`: 15类 + 11函数（工具集）

**架构变化说明**:
- 文件数：3个核心文件（保持不变）
- 重构策略：
  - `system_toolkit.py` → 拆分为 `core_engine.py` 和 `monitor_toolkit.py`（按职责拆分）
  - `monitor_system.py` → 保留并优化（监控核心）
- native_iocp集成：配置文件、缓存文件、日志文件全部使用native_iocp
- native_ipc集成：完全替代ZMQ，三条管道通信（alert_pipe、status_pipe、query_pipe）
- 配置文件化：新增system_config.yaml和threshold_config.yaml（增强可配置性）

**关键架构原则**:
1. **固定监控频率**：监控系统是数据提供者，监控频率固定不动态调整（系统指标1秒、硬件传感器5秒、SMART 60秒）
2. **智能负载均衡**：为LoadBalancer提供监控数据，LoadBalancer根据监控数据调整**业务模块**的并发数（不是监控频率）
3. **异步优先**：全面使用asyncio，关键路径使用native_iocp/native_ipc
4. **事件驱动**：所有组件通过vnpy EventEngine进行松耦合通信

### 2.1 自适应阈值管理（Part 1）

**核心类**: `AdaptiveThresholdManager`

**功能**: 统计学习 + 动态阈值调整

**方法接口**:
```python
__init__(config: ThresholdConfig = None)
update_metric(metric_name: str, value: float) -> None
check_threshold(metric_name: str, value: float) -> ThresholdResult
get_threshold(metric_name: str) -> Tuple[float, float]  # (mean, std_dev)
get_all_thresholds() -> Dict[str, Tuple[float, float]]
reset_metric(metric_name: str) -> None
```

**阈值配置**:
```python
@dataclass
class ThresholdConfig:
    cpu_warning: float = 80.0      # CPU警告阈值
    cpu_critical: float = 95.0     # CPU严重阈值
    memory_warning: float = 80.0   # 内存警告阈值
    memory_critical: float = 95.0  # 内存严重阈值
    disk_warning: float = 85.0     # 磁盘警告阈值
    disk_critical: float = 95.0    # 磁盘严重阈值
    adaptive_enabled: bool = True  # 启用自适应
    learning_window: int = 100     # 学习窗口大小
    std_multiplier: float = 2.0    # 标准差乘数
```

**自适应机制**:
- 滚动窗口统计（默认100个样本）
- 动态阈值 = 均值 + 2倍标准差
- 适用指标：CPU、内存、磁盘、网络、进程等

**native集成**:
- 首选 `native_statistics.create_streaming_metric(window_size=learning_window)` 维护滑动窗口
- 句柄更新失败会自动切换到 Python `deque` + NumPy，日志关键字 `native statistics`/`fallback`
- `NATIVE_STATISTICS_AVAILABLE` 由模块导入决定，可在运行中感知扩展状态

### 2.4 系统瓶颈分析器（Part 2）

**核心类**: `SystemBottleneckAnalyzer`

**功能**: 基于木桶理论的系统级瓶颈分析

**方法接口**:
```python
__init__(threshold_manager: AdaptiveThresholdManager = None)
analyze(system_metrics: Dict[str, Any], process_metrics: List[Dict[str, Any]], hardware_sensors: Dict[str, Any]) -> BottleneckResult
_calculate_resource_scores(...) -> Dict[str, float]
_identify_primary_bottleneck(scores: Dict[str, float]) -> Tuple[str, float]
_generate_suggestions(bottleneck_type: str, severity: str, scores: Dict[str, float]) -> List[str]
```

**瓶颈类型** (7种):
- `cpu`: CPU使用率过高
- `memory`: 内存不足
- `disk_io`: 磁盘I/O延迟
- `network`: 网络延迟或丢包
- `context_switch`: 上下文切换过多
- `thread_contention`: 线程竞争
- `temperature`: 温度过高

## 🔗 native_ipc深度集成方案

### 集成目标

将监控系统的ZMQ跨进程通信替换为native_ipc，提供更高效的原生Windows异步IPC通信。

**替代范围**：
- ✅ 监控进程 ↔ 主进程通信（替代ZMQ）
- ✅ 告警推送（替代ZMQ PUSH/PULL）
- ✅ 数据查询（替代ZMQ REQ/REP）
- ✅ 状态同步（替代ZMQ PUSH/PULL）
- ❌ UI ↔ data_module_vnpy直接调用（保持不变）

**通信架构对比**：
```
当前架构（已迁移）：监控进程 (native_ipc 客户端/服务端) ←Named Pipe→ 主进程 (native_ipc 服务端/客户端)
新架构：  监控进程 (native_ipc 客户端/服务端) ←Named Pipe→ 主进程 (native_ipc 服务端/客户端)
```

**核心目标**：
1. 替代ZMQ：监控进程与主进程通信使用native_ipc
2. 真异步：无线程池开销，更低延迟
3. Windows专属：充分利用Windows Named Pipe + IOCP机制

### 通信模式设计

**模式1: 请求-响应（REQ/REP）**
- 用途：监控数据查询、配置查询
- 实现：监控进程作为服务端，主进程作为客户端
- 管道名：`monitor_query`

**模式2: 发布-推送（PUSH/PULL）**
- 用途：告警推送、事件分发
- 实现：监控进程作为客户端推送，主进程作为服务端接收
- 管道名：`monitor_alerts`

**模式3: 状态同步（PUSH/PULL）**
- 用途：服务状态推送
- 实现：主进程作为客户端推送，监控进程作为服务端接收
- 管道名：`monitor_status`

## 🎯 智能负载均衡集成方案

### 核心定位

**数据提供者角色**：
- 系统监控模块是**数据提供者**（Provider），不是数据消费者（Consumer）
- 以固定高频采集系统指标，保证监控数据的稳定性和可靠性
- 通过事件引擎发布监控数据，供LoadBalancer等模块消费
- **禁止**根据系统压力动态调整监控频率（会导致监控数据质量下降）

### 设计原则

**监控频率固定**：
- ✅ 固定采集频率：系统指标1秒、硬件传感器5秒、SMART 60秒
- ✅ 用户可配置：通过配置文件调整采集频率（但运行时不动态变化）
- ✅ 底层优先级：监控开销必须<2% CPU，<100MB内存
- ✅ 独立进程运行：不受主进程业务压力影响
- ❌ 不使用智能负载均衡：避免形成负反馈循环

### 事件发布机制

**发布频率**（固定）：
- `EVENT_SYSTEM_METRICS`：每1秒发布一次（CPU、内存、磁盘、网络）
- `EVENT_HARDWARE_SENSORS`：每5秒发布一次（温度、风扇、功耗）
- `EVENT_BOTTLENECK_ANALYSIS`：每3秒发布一次（瓶颈分析结果）
- `EVENT_SMART_DATA`：每60秒发布一次（SMART硬盘健康数据）

**事件数据格式**：
```python
# EVENT_SYSTEM_METRICS 数据格式
```

### 与LoadBalancer的交互

**数据流向**：
```
┌─────────────────────┐
│  MonitoringProcess  │ (独立进程，固定1秒采集)
│  - 系统指标: 1秒    │
│  - 硬件传感器: 5秒  │
│  - CPU开销 < 2%    │
└──────────┬──────────┘
           │
           │ EVENT_SYSTEM_METRICS (每1秒发布)
           │ EVENT_HARDWARE_SENSORS (每5秒发布)
           ↓
┌─────────────────────┐
│    EventEngine      │
└──────────┬──────────┘
           │
           ├─→ UI层（显示监控数据）
           │
           ├─→ LoadBalancer（木桶理论评估）
           │   ↓
           │   动态调整业务并发数 ← 调整的是业务，不是监控！
           │   ├─→ DataCenter下载并发
           │   ├─→ 策略执行并发
           │   └─→ 其他业务模块并发
           │
           └─→ AlertEngine（生成告警）
```

**LoadBalancer如何使用监控数据**：
```python
class LoadBalancer:
    """智能负载均衡器（消费监控数据）"""

    def __init__(self, event_engine: EventEngine):
        self.event_engine = event_engine
        self._latest_system_metrics: Optional[Dict] = None

        # 订阅系统监控事件
        self.event_engine.register(EVENT_SYSTEM_METRICS, self._on_system_metrics)

    def _on_system_metrics(self, event: Event):
        """接收系统监控数据"""
        self._latest_system_metrics = event.data

    def get_optimal_config(self, task: Task) -> Dict[str, int]:
        """根据系统状态计算最优配置（调整业务并发，不是监控频率）"""
        if not self._latest_system_metrics:
            return self._get_default_config(task)

        # 使用木桶理论评估系统压力
        pressure_score = self._calculate_pressure_score(self._latest_system_metrics)

        # 根据压力动态调整业务并发数
        if pressure_score < 40:
            # 系统压力大，降低业务并发
            return {"max_workers": 4, "max_coroutines": 500}
        elif pressure_score < 60:
            return {"max_workers": 8, "max_coroutines": 1000}
        else:
            # 系统压力小，提高业务并发
            return {"max_workers": 16, "max_coroutines": 2000}

    def _calculate_pressure_score(self, metrics: Dict) -> float:
        """计算系统压力评分（木桶理论：取最小值）"""
        cpu_score = 100 - metrics.get("cpu_percent", 0)
        memory_score = 100 - metrics.get("memory_percent", 0)
        disk_io = metrics.get("disk_io_read_mb_s", 0) + metrics.get("disk_io_write_mb_s", 0)
        disk_score = max(0, 100 - (disk_io / 500 * 100))

        # 木桶理论：取最短板
        return min(cpu_score, memory_score, disk_score)
```

## 📝 关键设计模式和最佳实践

### 1. 单例模式

**使用场景**:
- `ErrorCounter`: 全局错误计数器
- `WMISmartMonitor`: WMI监控器
- `BusinessMetricsCollector`: 业务指标采集器

**实现方式**: 双重检查锁 + 全局函数

---

### 2. 上下文管理器

**使用场景**:
- 阶段切换（通过set_stage手动管理）

---

### 3. 混合并发模型

**架构**: asyncio主循环 + ThreadPoolExecutor后台线程

**原则**:
- I/O密集（网络、native_ipc）：asyncio协程
- CPU密集（计算）：asyncio协程
- 阻塞I/O（磁盘、WMI、COM）：后台线程池

---

### 4. 两阶段就绪模型

**问题**: 慢速组件阻塞启动流程

**解决方案**:
- Level 1: 通信层就绪（2-3秒）
- Level 2: 业务功能完整（后台异步）

---

### 5. 降级策略

**原则**: 核心功能不依赖可选组件

**实现**:
- LibreHardwareMonitor不可用 → 基础监控继续运行
- 测速服务器不可用 → 自动降级到备用服务器
- WMI权限不足 → SMART数据标记"未知"

---

### 6. 缓存优化

**策略**:
- RuleCache: LRU + 5秒TTL
- BandwidthMonitor: 结果缓存
- AdaptiveThresholdManager: 滚动窗口统计

---

### 7. 节流机制

**策略**:
- ProgressThrottler: 500ms聚合窗口
- EventEngine节流: event_throttled目标
- 定期任务: 不同频率（1秒/2秒/3秒/5秒）

```bash
cd backend/infrastructure/native/native_ipc
```

**管道连接检查**:

- 检查是否有其他进程占用管道名称

2. 网络连接是否正常
3. 防火墙是否阻止测速站点访问
4. 日志中是否有服务器不可用的错误

---

### 问题6: native_ipc通信失败

**检查点**:
1. C扩展是否已编译（见问题1）
2. 管道是否已创建（检查服务端是否启动）
3. 管道名称是否正确（`monitor_alerts`, `monitor_status`, `monitor_query`）
4. 是否有权限访问Named Pipe（检查Windows安全设置）
5. 客户端和服务端是否在同一个Windows会话中运行

**常见错误**:
- `IPC extension not available`: C扩展未编译，需要编译C扩展
- `Pipe not opened`: 管道未打开，确保在`async with`中使用
- `Pipe not connected`: 管道未连接，确保服务端已创建管道
- `Permission denied`: 权限不足，检查Named Pipe访问权限

**调试方法**:
```python
from backend.infrastructure.native.native_ipc import IPC_AVAILABLE
```

## Socket缓冲区监控（v0.51新增）

### 功能说明

Socket缓冲区监控用于实时监控系统中TCP连接的接收和发送缓冲区大小及使用情况，帮助识别网络性能瓶颈。

### 监控指标

**指标名称**: `socket_buffer_info`
**采集频率**: 1秒（与系统资源指标同步）
**数据路径**: `system.network_subsystem.socket_buffer_info`

**核心指标**:
1. `recv_buffer_size_avg`: 平均接收缓冲区大小（字节）
2. `send_buffer_size_avg`: 平均发送缓冲区大小（字节）
3. `recv_buffer_usage_ratio`: 接收缓冲区使用率（%，估算值）
4. `send_buffer_usage_ratio`: 发送缓冲区使用率（%，估算值）
5. `tcp_connections`: TCP连接数
6. `established_connections`: ESTABLISHED状态连接数

### 预警阈值

- **警告阈值**: 缓冲区使用率 > 80%
- **严重阈值**: 缓冲区使用率 > 95%
- **缓冲区大小警告**: 缓冲区大小 < 64KB（可能影响性能）

### 前端UI展示

1. **统一监控卡片**: 在UnifiedMonitorCard底部显示Socket缓冲区信息
   - 格式：`Socket缓冲区: 接收XXKB(XX%) 发送XXKB(XX%)`
   - 颜色：使用率超过阈值时显示橙色（警告）或红色（严重）

2. **详细数据表格**: 在系统状态详细表格中显示
   - Socket接收缓冲区（大小/使用率）
   - Socket发送缓冲区（大小/使用率）
   - TCP连接数（ESTABLISHED/总数）

### 后端实现

**核心方法**: `SystemMonitor.get_socket_buffer_info()`
- 使用 `psutil.net_connections()` 获取所有网络连接
- 通过 `socket.fromfd()` 和 `getsockopt(SO_RCVBUF/SO_SNDBUF)` 获取缓冲区大小
- 缓冲区使用率通过连接状态和网络I/O速率估算

**集成位置**:
- `get_network_subsystem_metrics()` 方法中自动调用
- 数据自动包含在监控进程的 `network_subsystem` 数据中

**阈值管理**:
- 在 `AdaptiveThresholdManager` 中注册了以下指标：
  - `socket_recv_buffer_usage_ratio`: 警告80%，严重95%
  - `socket_send_buffer_usage_ratio`: 警告80%，严重95%

### 使用示例

```python
# 获取Socket缓冲区信息
from backend.infrastructure.system_vnpy import SystemMonitor

monitor = SystemMonitor()
buffer_info = monitor.get_socket_buffer_info()

print(f"接收缓冲区: {buffer_info['recv_buffer_size_avg']/1024:.0f}KB")
print(f"接收使用率: {buffer_info['recv_buffer_usage_ratio']:.1f}%")
print(f"发送缓冲区: {buffer_info['send_buffer_size_avg']/1024:.0f}KB")
print(f"发送使用率: {buffer_info['send_buffer_usage_ratio']:.1f}%")
```

### 注意事项

1. **权限要求**: 获取socket缓冲区信息可能需要管理员权限（某些系统）
2. **跨平台兼容**: Windows和Linux平台使用不同的socket获取方式
3. **使用率估算**: 缓冲区使用率是估算值，基于连接状态和网络I/O速率计算
4. **性能影响**: 大量连接时可能影响性能，目标执行时间 < 10ms

### 日志埋点

**埋点位置**: `monitor_system.py` 的 `get_socket_buffer_info()` 方法

**日志类型**:
- `[SOCKET-BUFFER]` - Socket缓冲区相关日志
- `[NETWORK-SUBSYSTEM]` - 网络子系统集成日志

**日志级别**:
- `DEBUG`: 数据采集过程、统计信息
- `INFO`: 警告信息（使用率 > 80%）
- `WARNING/ALERT`: 严重告警（使用率 > 95%）

**日志示例**:
```python
# DEBUG级别
logger.debug("[SOCKET-BUFFER] 获取到 150 个网络连接", extra={"log_type": "SYSTEM"})
logger.debug("[SOCKET-BUFFER] 统计完成: TCP连接=120, ESTABLISHED=85, ...", extra={"log_type": "SYSTEM"})

# INFO级别（警告）
logger.info("[SOCKET-BUFFER] ⚠️ Socket缓冲区使用率警告: 接收=85.2%, 发送=82.1%", extra={"log_type": "SYSTEM"})

# WARNING级别（严重告警）
logger.warning("[SOCKET-BUFFER] ⚠️ Socket缓冲区使用率严重告警: 接收=96.5%, 发送=94.2%", extra={"log_type": "ALERT"})
```
