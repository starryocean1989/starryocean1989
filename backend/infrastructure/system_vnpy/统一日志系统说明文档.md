## 一、系统概述

### 1.1 设计目标

统一日志系统是项目的核心基础设施，实现了：

1. **统一日志中心**：所有日志通过 `LoggingHub` 统一处理
2. **简化路由规则**：硬编码路由规则，无需配置文件
3. **性能优化**：进度节流、批量数据库操作、有序队列
4. **不丢失日志**：MemoryHandler缓冲 + PersistentBufferHandler持久化
5. **有序日志输出**：启动阶段使用有序队列，确保日志按顺序展示
6. **多进程支持**：MultiProcessLogCollector统一收集子进程日志
7. **核心代码集中**：所有核心逻辑都在 `logging_system.py`，便于调试

### 1.2 核心特性

- ✅ **硬编码路由规则**：简化架构，无需配置文件
- ✅ **7种日志类型**：SYSTEM、PROGRESS、NOTIFICATION、ALERT、USER_FEEDBACK、DEBUG、STAGE_NODE
- ✅ **5种输出目标**：file、console、database、event、event_throttled
- ✅ **进度节流**：500ms聚合窗口，减少高频进度日志
- ✅ **批量数据库写入**：批量插入，减少数据库I/O
- ✅ **多进程日志收集**：使用multiprocessing.Queue统一收集子进程日志
- ✅ **持久化缓冲**：日志系统初始化前写入临时文件，防止崩溃导致日志丢失
- ✅ **有序队列**：支持启动、批量下载、数据扫描等所有并发场景的有序输出
- ✅ **单文件架构**：所有核心代码在 `logging_system.py`（2230行），便于调试

### 1.3 架构简化

**v6.0 简化重构版**：
- ❌ 移除四层路由引擎（场景、模块、阶段、全局）
- ❌ 移除YAML配置文件（4个配置文件）
- ❌ 所有日志输出统一归档在 `logs/` 目录
- ✅ 硬编码路由规则（在 `LoggingHub._get_targets()` 中）
- ✅ 单文件架构（`logging_system.py`）
- ✅ 核心代码集中（所有调试都在 `logging_system.py`）

## 二、架构设计

### 2.1 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                     Python Logging                          │
│                  (所有logger统一处理)                       │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ↓
┌─────────────────────────────────────────────────────────────┐
│                    LoggingHub                               │
│              (统一日志中心，继承logging.Handler)            │
│                                                              │
│  - 拦截所有日志记录                                         │
│  - 转换为UnifiedLogRecord                                  │
│  - 硬编码路由规则（_get_targets）                          │
│  - 根据路由结果分发到不同目标                               │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ↓
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ↓                  ↓                  ↓
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│   Console    │  │     File     │  │   Database   │
│  (Terminal)  │  │ (EventLogFile│  │  (Batched)   │
│              │  │   Handler)   │  │              │
└──────────────┘  └──────────────┘  └──────────────┘
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                           ↓
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ↓                  ↓                  ↓
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│    Event     │  │EventThrottled│  │OrderedQueue  │
│  (NOTIFICATION│  │  (PROGRESS)  │  │  (启动阶段)  │
│    ALERT)    │  │              │  │              │
└──────────────┘  └──────────────┘  └──────────────┘
```

### 2.2 数据流

```
1. 埋点阶段：
   logger.info("消息", extra={"log_type": "SYSTEM"})
   ↓
2. 拦截阶段：
   LoggingHub.emit(LogRecord)
   ↓
3. 转换阶段：
   UnifiedLogRecord = _convert_to_unified_record(LogRecord)
   ↓
4. 路由阶段：
   targets = _get_targets(UnifiedLogRecord)  # 硬编码规则
   ↓
5. 分发阶段：
   _dispatch(targets, UnifiedLogRecord)
   ├─ file → EventLogFileHandler.emit()
   ├─ console → _to_console() → OrderedLogQueue (启动阶段)
   ├─ database → _to_database_batched()
   ├─ event → _to_event() → EventEngine.put()
   └─ event_throttled → _to_event_throttled() → ProgressThrottler
```

### 2.3 核心设计原则

1. **统一拦截**：所有日志都通过 `LoggingHub` 统一处理
2. **硬编码路由**：路由规则硬编码在 `_get_targets()` 方法中，无需配置文件
3. **有序输出**：启动阶段使用 `OrderedLogQueue` 确保日志按顺序展示
4. **不丢失日志**：`MemoryHandler` + `PersistentBufferHandler` 双重保障
5. **多进程支持**：`MultiProcessLogCollector` 统一收集子进程日志
6. **单文件架构**：所有核心代码在 `logging_system.py`，便于调试

### 3.2 EventLogFileHandler（事件日志文件Handler）

**文件**: `backend/infrastructure/system_vnpy/logging_system.py` (Part 7, 第554行)

**核心类**:
```python
class EventLogFileHandler(logging.Handler):
    """事件日志文件Handler - 为每个事件创建独立的日志文件

    优化特性：
    - 支持同一事件的嵌套调用（引用计数管理）
    - 自动合并多个元数据到同一文件
    - 确保每个事件只生成一个日志文件
    """
```

**主要方法**:
- `start_event(event_name, metadata)` - 开始事件日志（支持嵌套调用和元数据合并）
- `end_event(success, summary)` - 结束事件日志（使用引用计数，只有引用计数为0时才真正结束）
- `emit(record)` - 写入日志到文件

**文件输出**:
- 常规日志：`logs/terminal.log`（所有日志全量）
- 事件日志：`logs/{event_name}_YYYYMMDD_HHMMSS.log`（支持的事件，每个事件只生成一个文件）

**事件复用机制**（v6.1优化）:
1. **嵌套调用支持**：如果同一事件名称被多次调用 `start_event()`，会自动复用现有文件
2. **引用计数管理**：每次 `start_event()` 增加引用计数，每次 `end_event()` 减少引用计数
3. **元数据合并**：多个元数据会自动合并到同一文件，在文件头中显示所有元数据
4. **单文件保证**：每个事件只生成一个日志文件，即使有多个嵌套调用

**示例**:
```python
# orchestrator.py
with event_log_process("application_startup", {"mode": "orchestrator"}):
    # 创建文件: application_startup_20251105_161223.log

    # backend_init.py（嵌套调用）
    with event_log_process("application_startup", {"mode": "backend_init"}):
        # 复用同一文件，追加元数据到文件头
        # 引用计数: 2

    # 引用计数: 1（backend_init结束）
# 引用计数: 0（orchestrator结束，文件关闭）
```

### 3.5 MultiProcessLogCollector（多进程日志收集器）

**文件**: `backend/infrastructure/system_vnpy/logging_system.py` (Part 5, 第421行)

**核心类**:
```python
class MultiProcessLogCollector:
    """多进程日志收集器 - 通过 SyncManager 托管进程安全队列"""
```

**主要方法**:
- `start()`：启动 SyncManager 与 QueueListener，接收来自子进程的日志。
- `stop()`：安全停止监听线程与 SyncManager。
- `get_queue()`：返回 QueueProxy，供主进程内部直接写入（如启动阶段回放）。
- `get_bridge_token()`：将 QueueProxy 元数据序列化为 Base64，便于通过环境变量传递。
- `load_queue_from_env()`：在子进程恢复 QueueProxy，失败时返回 `None` 以触发降级逻辑。

**启动阶段落地流程**:
1. `LoggingInitStage` 创建 `MultiProcessLogCollector`，调用 `start()` 启动并记录 `context.log_queue`、`context.log_queue_token`。
2. `DataLauncherWorker`、`MonitorLauncherWorker` 启动子进程时，将 `context.log_queue_token` 写入环境变量 `LOGGING_QUEUE_TOKEN`。
3. 子进程执行 `load_queue_from_env()` → `setup_subprocess_logging(queue)`，自动为根 logger 注入 `QueueHandler`。
4. 若任一步骤失败，会记录 `WARNING` 并回退到子进程本地日志，主进程启动不会中断。

**代码示例**:
```python
import os
import subprocess
from backend.infrastructure.system_vnpy.logging_system import (
    MultiProcessLogCollector,
    setup_subprocess_logging,
    load_queue_from_env,
    LOGGING_QUEUE_TOKEN_ENV,
)

# 主进程
collector = MultiProcessLogCollector(logging_hub)
collector.start()
context.log_queue = collector.get_queue()
context.log_queue_token = collector.get_bridge_token()

env = os.environ.copy()
if context.log_queue_token:
    env[LOGGING_QUEUE_TOKEN_ENV] = context.log_queue_token
subprocess.Popen([...], env=env)

# 子进程
queue_proxy = load_queue_from_env()
if queue_proxy:
    setup_subprocess_logging(queue_proxy)
```

> ℹ️ `LOGGING_QUEUE_TOKEN_ENV` 默认为 `"LOGGING_QUEUE_TOKEN"`，其值为 Base64 编码的 pickle 数据，
>   包含 SyncManager 地址、`authkey` 与 QueueProxy。若环境变量缺失或解码失败，`load_queue_from_env()` 会返回 `None`，
>   子进程将继续使用本地日志 Handler，同时主进程在启动阶段输出 `WARNING` 以提示桥接降级。
```

## 五、路由机制

### 5.1 硬编码路由规则

**位置**: `LoggingHub._get_targets()` (第1123行)

**路由规则**（硬编码）:
```python
def _get_targets(self, record: UnifiedLogRecord) -> List[str]:
    """获取路由目标（简化的硬编码规则）

    路由规则（硬编码）：
    - Terminal输出：WARNING/ERROR/CRITICAL + STAGE_NODE.INFO
    - 数据库输出：与terminal一致（WARNING/ERROR/CRITICAL + STAGE_NODE.INFO）
    - 文件输出：所有日志都写入文件（全量）
    - 事件引擎：NOTIFICATION和ALERT类型（用于内部通知）
    - 节流事件：PROGRESS类型（500ms聚合）
    """
    targets = []

    # 文件输出：所有日志都写入文件（全量）
    targets.append("file")

    # Terminal输出：WARNING/ERROR/CRITICAL + STAGE_NODE.INFO
    if record.level >= logging.WARNING or (
        record.type == LogType.STAGE_NODE and record.level == logging.INFO
    ):
        targets.append("console")

    # 数据库输出：与terminal一致
    if record.level >= logging.WARNING or (
        record.type == LogType.STAGE_NODE and record.level == logging.INFO
    ):
        targets.append("database")

    # 事件引擎：NOTIFICATION和ALERT类型
    if record.type in (LogType.NOTIFICATION, LogType.ALERT):
        targets.append("event")

    # 节流事件：PROGRESS类型
    if record.type == LogType.PROGRESS:
        targets.append("event_throttled")

    return targets
```

### 5.2 路由目标说明

| 目标 | 说明 | 输出内容 |
|------|------|----------|
| **file** | 文件输出 | 所有日志（全量） |
| **console** | Terminal输出 | WARNING/ERROR/CRITICAL + STAGE_NODE.INFO |
| **database** | 数据库输出 | 与console一致 |
| **event** | 事件引擎 | NOTIFICATION和ALERT类型 |
| **event_throttled** | 节流事件 | PROGRESS类型（500ms聚合） |

### 5.3 有序队列机制

**启动阶段**：启用 `OrderedLogQueue`，确保console和database输出有序

**正常运行阶段**：禁用有序队列，直接输出

**判断逻辑**:
```python
# 如果启用了有序队列，且目标是console或database，添加到有序队列
if self._ordered_queue_enabled and self._ordered_log_queue is not None:
    needs_ordered_output = any(target in ("console", "database") for target in targets)
    if needs_ordered_output:
        # 添加到有序队列
        self._ordered_log_queue.add_log(record, sequence)
        return  # 不直接输出，等待有序队列处理
```

## 九、性能优化

### 9.1 进度节流

**机制**: `ProgressThrottler` (500ms聚合窗口)

**工作原理**:
1. 聚合500ms内的所有PROGRESS类型日志
2. 在聚合窗口中，只发送最后一条日志
3. 在日志的details中添加`_throttled_count`字段，表示聚合的日志数量

**效果**: 减少高频进度日志，降低I/O压力

### 9.2 批量数据库写入

**机制**: 批量插入，减少数据库I/O

**配置**:
- 缓冲区大小：10条
- 刷新间隔：5秒
- 自动刷新：缓冲区满时立即刷新

**效果**: 减少数据库写入次数，提高性能

### 9.3 有序队列优化

**机制**: `OrderedLogQueue` 按执行时间排序

**工作原理**:
1. 日志按执行时间戳排序（而非序列号）
2. 超时机制：超过30秒即使前面的日志未到也输出
3. 后台线程定期检查并输出超时的日志

**效果**: 确保并发场景时日志按顺序展示，避免日志混乱

### 9.4 多进程日志收集

**机制**: `MultiProcessLogCollector` 通过 `SyncManager` 托管队列，并下发Base64 token

**工作原理**:
1. 主进程创建 `MultiProcessLogCollector`，启动 `SyncManager` 并生成队列代理 token。
2. `LoggingInitStage` 将 token 保存到 `StartupContext`，各子进程在启动时写入 `LOGGING_QUEUE_TOKEN` 环境变量。
3. 子进程调用 `load_queue_from_env()` + `setup_subprocess_logging()` 恢复队列代理，通过 QueueHandler 将日志发送回主进程。
4. 若环境变量缺失或还原失败，子进程记录 `WARNING` 并回退到本地日志，主进程同时输出降级提示。
5. 主进程 `QueueListener` 统一收集并转发到 `LoggingHub`，保持日志顺序。

**效果**: 统一收集子进程日志并支持降级兜底，避免因桥接失败导致的日志丢失。

### 9.5 持久化缓冲

**机制**: `PersistentBufferHandler` 双重保障

**工作原理**:
1. 内存缓冲：快速缓冲日志（容量10000条）
2. 文件缓冲：超过容量后写入临时文件
3. 日志系统初始化后，重放所有缓冲日志

**效果**: 防止进程崩溃导致日志丢失

## 十、常见问题

### 10.1 日志没有输出到Terminal

**问题**: 日志没有输出到Terminal

**原因**:
1. 日志级别不够（DEBUG/INFO级别不会输出到Terminal，除非是STAGE_NODE类型）
2. 日志类型不是STAGE_NODE（只有STAGE_NODE.INFO会输出到Terminal）
3. LoggingHub未正确初始化

**解决方案**:
1. 使用STAGE_NODE类型：`extra={"log_type": "STAGE_NODE"}`
2. 使用WARNING及以上级别：`logger.warning("消息")`
3. 检查LoggingHub是否已初始化：`get_logging_hub()`

### 10.2 日志没有写入文件

**问题**: 日志没有写入文件

**原因**:
1. EventLogFileHandler未正确注入
2. 日志文件目录不存在或没有写权限
3. 事件日志流程未启动

**解决方案**:
1. 检查EventLogFileHandler是否已注入：`hub.set_event_log_handler(handler)`
2. 检查logs目录是否存在且有写权限
3. 启动事件日志流程：`start_event_process("event_name")`

### 10.3 日志没有写入数据库

**问题**: 日志没有写入数据库

**原因**:
1. DatabaseManager未注入到LoggingHub
2. 数据库连接失败
3. 批量缓冲区未刷新

**解决方案**:
1. 注入DatabaseManager：`hub.set_db_manager(db_manager)`
2. 检查数据库连接
3. 手动刷新缓冲区：`hub._flush_db_batch()`

### 10.4 启动阶段日志顺序混乱

**问题**: 启动阶段日志顺序混乱

**原因**:
1. 有序队列未启用
2. 有序队列未正确配置

**解决方案**:
1. 启用有序队列：`hub.enable_ordered_queue()`
2. 设置有序队列：`hub.set_ordered_log_queue(ordered_queue)`

### 10.5 子进程日志丢失

**问题**: 子进程日志丢失

**原因**:
1. MultiProcessLogCollector未启动
2. 子进程未配置日志

**解决方案**:
1. 启动收集器：`collector.start()`
2. 配置子进程日志：`setup_subprocess_logging(queue)`

### 10.6 日志系统初始化前的日志丢失

**问题**: 日志系统初始化前的日志丢失

**原因**:
1. MemoryHandler未设置
2. PersistentBufferHandler未设置

**解决方案**:
1. 设置MemoryHandler：`setup_memory_logging()`
2. 设置PersistentBufferHandler：`setup_memory_logging()`会自动创建

**核心策略**: 使用STAGE_NODE日志类型 + 事件日志流程管理
